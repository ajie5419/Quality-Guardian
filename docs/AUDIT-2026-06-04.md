## 高危问题（5 项）

### 1. 错误码类型不一致 + 前端分级逻辑失效

- **现象**：后端 `BusinessError.code` 是字符串（如 `'BAD_REQUEST'`），但响应体顶层 `code` 字段永远输出 `-1`，导致前端分级拦截完全失效。
- **证据**：
  - `apps/backend/utils/response.ts:52` — 统一将 code 写死为 `-1`
  - `apps/web-antd/src/api/request.ts:127` — 拦截器判断 `code >= 1000 && code < 5000`，永远不命中
- **影响**：所有业务错误（校验失败、权限拒绝、状态冲突）全部掉进兜底分支，前端无法按严重程度选择 warning / error / notification 提示，用户体验完全退化。注：前端已有临时 commit 修复了"能显示 message 字符串"，但分级逻辑本身仍然坏的。
- **修复方向**：在 `response.ts` 中将 `BusinessError.code` 透传到响应 `code` 字段，并与前端约定数值区间映射（如 4xx → warning，5xx → error）。

---

### 2. 登录暴力破解无防护

- **现象**：登录接口无任何频率限制、失败计数或账号锁定机制。
- **证据**：`apps/backend/modules/user/auth.service.ts` 全文无 `rate-limit` / `throttle` / `attempts` / `lockout` 相关逻辑，登录失败仅记日志。
- **影响**：攻击者可对任意账号发起无限次字典攻击，无任何阻断。
- **修复方向**：在 `auth.service.ts` 中引入 IP + 账号双维度失败计数（存 Redis），超过阈值（如 5 次/10 分钟）返回 429 并临时锁定账号。

---

### 3. 水平越权（IDOR）— 多模块缺失所有权校验

- **现象**：`data-scope` 中间件仅覆盖 4 个模块（after-sales / inspection / supplier / work-order），quality-loss / metrology / knowledge 等模块的写操作完全没有所有权校验。
- **证据**：
  ```typescript
  // apps/backend/modules/quality-loss/quality-loss-record-maintenance.service.ts:10
  // deleteRecord 仅做 findFirst 后软删，不查 createdBy / orgId
  ```
- **影响**：任何已登录用户只要知道记录 ID，即可删除或修改不属于自己部门的质量损失记录、计量记录等业务数据，绕过数据权限边界。
- **修复方向**：对未覆盖模块的 delete / put 路由补充所有权断言（比对 `createdBy` 或 `orgId` 与当前用户），或将 `data-scope` 中间件扩展到这些模块。

---

### 4. inspection-request close 存在并发竞态

- **现象**：关闭检验请求的状态检查在事务外执行，两个并发请求均能通过检查后重复关闭。
- **证据**：
  ```typescript
  // apps/backend/modules/inspection/inspection-request-close.service.ts:57-143
  // findFirst 检查 status === 'CLOSED' 在事务外
  // 后续多步业务逻辑，最后才进 $transaction
  ```
- **影响**：并发场景下两个 close 请求均绕过状态检查，导致重复关闭、重复触发后续联动逻辑（评分、通知等），与 dispatch 模块曾出现的同款竞态一致。
- **修复方向**：将状态检查移入 `$transaction` 内部，使用 `select ... for update` 或 Prisma 的 `updateMany + where: { status: { not: 'CLOSED' } }` 做原子状态守卫。

---

### 5. 异常类型混乱导致校验错误对用户不可见

- **现象**：三种错误风格并存：`BusinessError`（规范）、`Error('VALIDATION:...')`（可被转换）、`Error('中文消息')`（无法识别，直接 500）。
- **证据**：
  - 第三种风格约 15 处，集中在 `apps/backend/modules/metrology/metrology-borrow.service.ts:76,79,82` 等
  - `legacyErrorToBusinessError` 只能处理 `VALIDATION:` 前缀，无法识别裸中文 Error
- **影响**：叠加 #1 的根因，计量模块所有业务校验错误（如借用数量超限、设备状态不符）对用户都表现为无结构的 `message.error`，完全失去语义。
- **修复方向**：统一改用 `BusinessError`，清除 `Error('中文...')` 风格；或扩展 `legacyErrorToBusinessError` 以兜底转换任意中文 Error 为 400 级别响应。

## 待补强的硬约束

建议在 `CONSTRAINTS.md` 中追加以下规则：

1. **错误码契约**：所有业务错误必须抛 `BusinessError(code: string, message: string, httpStatus: number)`，禁止使用 `Error('中文字符串')` 或裸 `throw new Error()`；response.ts 必须将 `BusinessError.code` 透传到响应体。
2. **并发写操作必须使用事务守卫**：凡是先 `findFirst` 检查状态、再执行写操作的流程，状态检查必须在 `$transaction` 内完成，或使用 `updateMany + where 条件` 做原子守卫。
3. **新增写路由必须声明所有权断言**：涉及用户/部门私有数据的 delete / put 路由，必须在 service 入口处校验 `createdBy` 或 `orgId` 与当前用户一致，或通过 `data-scope` 中间件覆盖。
4. **禁止静默 catch**：`} catch {}` 或 `} catch (e) {}` 形式一律禁止；最低要求是 `logger.error(e, 'context')` 后再决定是否重新抛出。
