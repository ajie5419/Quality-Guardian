# 需求单：后端统一授权框架（写操作权限强制）

**版本**：v1　**优先级**：P0　**关联**：docs/permission-audit-report.md（摸底报告）、docs/audit-action-plan.md 第 2/3 项
**预估规模**：框架阶段 1-2 周；存量迁移按批次 2-4 周

---

## 1. 背景与目标

### 1.1 现状问题（有数据证据，见摸底报告）

- 189 个写端点中约 **140 个只有登录校验**，无任何业务权限/所有权校验：任何有账号的人可直接调用接口删除/修改检验记录、计量器具、BOM/DFMEA/ITP、监造项目等核心质量数据
- **52 个权限码只控制前端按钮显隐**，后端消费权限码的业务点仅 4 个
- 校验实现**五套并存**（requireSystemAdmin / 权限码 / 自建 access 服务 / dataScope / createdBy 手动比对），新模块不知道该用哪套，多数不用
- 新增端点**无"必须声明权限"的门禁**，问题随每个新功能持续复制

### 1.2 目标

1. **统一授权机制**：所有写操作（增/删/改）必须经过统一授权校验，声明缺失 = 默认拒绝（fail-closed）
2. **新增即登记**：门禁强制——新写端点不声明权限规则，CI 直接拦截
3. **存量分批补齐**：按模块批次迁移，先核心质量数据，后其余
4. 数据范围（部门/本人隔离）同一机制覆盖写路径（与第 3 项联动）

## 2. 设计原则

| # | 原则 | 说明 |
|---|---|---|
| P1 | **声明制** | 每个写端点必须声明授权规则（权限码 / 所有权 / 数据范围），声明是代码的一部分 |
| P2 | **默认拒绝** | 未声明或声明缺失 → 拒绝访问（403），不允许"没声明就当公开" |
| P3 | **单一入口** | 授权校验由框架统一执行（中间件），业务代码不各自手写 |
| P4 | **分层校验** | 三层：权限码（能不能做）→ 所有权（是不是自己的）→ 数据范围（在不在范围内），按端点声明组合 |
| P5 | **复用现网资产** | 权限码复用现有 52 个 authCode + rbac_role_permissions；范式复用 inspection-issue-access.service 模式 |

## 3. 功能需求（FR）

| # | 需求 | 说明 |
|---|---|---|
| FR1 | 写端点授权声明机制 | 每个写端点（post/put/delete/patch）声明授权规则：所需权限码、是否要求所有权（createdBy 比对）、是否要求数据范围过滤。声明位置由开发从"路由文件内声明 / 模块声明文件集中声明 / 中间件配置表"中选一（推荐路由文件内声明，就近可见） |
| FR2 | 框架统一执行 | 新增授权中间件，对所有写请求执行：解析声明 → 无声明则拒绝 → 按声明校验权限码（RbacService.getUserPermissionCodes）→ 按需校验所有权/数据范围。读端点暂不强制（本期只收写） |
| FR3 | 权限码字典治理 | 声明引用的权限码必须来自 @qgs/shared 共享枚举（如 PERMISSION_CODES 模式），禁止自由字符串；新码先入字典 + rbac_permissions 表，再被引用 |
| FR4 | 新增即登记门禁 | 架构门禁新增规则：api 写端点文件无授权声明 → CI 拦截（增量检查，存量入 baseline 分批消化） |
| FR5 | 数据范围写路径接入 | 声明了数据范围的写端点，写入前校验目标数据在操作者范围内（复用 DataScopeService，范式见 quality-loss 的 assertDeleteAccess） |
| FR6 | 错误响应统一 | 拒绝时返回标准 403（BusinessError FORBIDDEN + 明确消息），前端按错误码分级提示 |
| FR7 | 管理员豁免规则明确 | super 角色默认拥有全部权限码（现有 RBAC_SUPER_MERGE_ALL_CODES 机制保留），豁免规则由框架统一处理，禁止散落各处 |

## 4. 验收标准（AC）

| # | 场景 | 预期 |
|---|---|---|
| AC1 | 普通账号（无权限码）直接调用"删除检验记录"接口 | **403 拒绝**，提示无权限 |
| AC2 | 有"删除检验记录"权限码的账号调用同一接口 | 通过（进入业务逻辑） |
| AC3 | 无权限码账号删除他人创建的记录（该模块声明了所有权校验） | **403 拒绝**（所有权断言生效） |
| AC4 | 数据范围开启后，DEPT 范围用户删除其他部门记录（声明了范围校验的端点） | **403 拒绝** |
| AC5 | 新提交一个写端点文件且未声明授权规则 | CI 门禁**拦截**（check:qms-arch 失败） |
| AC6 | 新提交的写端点声明了规则、引用了不存在的权限码 | CI 门禁拦截（码不在字典） |
| AC7 | 声明引用了 @qgs/shared 枚举中已存在的权限码 | 通过 |
| AC8 | super 管理员调用任意写端点 | 通过（豁免机制） |
| AC9 | 拒绝响应为标准格式：HTTP 403 + `{code:-1, error:{code:'FORBIDDEN'}, message}` | 通过 |
| AC10 | 前端：被拒操作显示"无权限"类提示，不出现 500/白屏 | 通过 |
| AC11 | 存量迁移：检验记录模块全部写端点补齐声明后，模块原有功能回归测试通过 | 通过 |
| AC12 | 匿名公开端点（/api/qms/public/**）不受影响，保持可匿名 | 通过 |

| 写端点现状清单 | 189 个，约 140 个需补声明 | docs/permission-audit-report.md |

**实现注意**：
1. 中间件顺序：授权中间件必须在认证（3.auth）之后；数据范围中间件可与授权合并或保持独立，避免重复查库（现有每次请求 3-4 次 DB 查询，需加缓存）
2. 门禁用 AST 检测（写方法 + 无声明），与 B-EC 同机制；存量先入 baseline，迁移一个删一条
3. 权限码与菜单按钮的映射保持单一来源：声明引用的码 = 菜单按钮 authCode = rbac_permissions 行，三者必须一致（门禁可校验声明码存在于共享枚举）
4. 读端点本期不做强制（避免超大回归面），但框架预留扩展

| 批次 | 内容 | 验收 |
|---|---|---|
| **Phase 1 框架**（1-2 周） | 声明机制 + 授权中间件 + 门禁规则 + 错误响应 + 缓存 | AC5/AC6/AC7/AC8/AC9/AC10 通过；存量 0 迁移（全入 baseline） |

| **Phase 3 其余**（1-2 周） | 售后、供应商、工单、质量损失、任务派发、车辆验收、汇报、AI 等剩余模块 | 全部 AC 通过；baseline 清零 |

## 7. 回归范围

- 全部业务模块的既有功能（重点：各模块列表/详情/增删改主流程）
- 前端按钮显隐与后端校验的一致性（按钮可见但接口 403 属预期，需提示友好）
- 匿名公开链路（报检、计量借还）不受影响
- RBAC 角色权限配置界面（权限码增删后正常）

## 8. 风险与说明

- **最大风险是误伤**：存量补齐期间若权限码数据（rbac_role_permissions）与角色配置不匹配，可能出现"有权限的用户被 403"。Phase 2 每个模块迁移后需真机验证各角色账号
- 权限码数据现状需先盘点：rbac_permissions 表与菜单 authCode 的一致性、各角色已分配码（建议 Phase 1 前置一个小任务）
- 离职/禁用账号 token 7 天有效问题（token 无服务端吊销）不在本需求单范围，建议单独排期
- 本框架只解决"写操作授权"；读端点的数据隔离依赖第 3 项（数据范围），需并行推进

## 9. 不做（本期范围外）

- 读端点强制授权（预留）
- 细粒度行级权限（按行可见性）——本期只做"操作级"授权
- token 吊销/会话管理
- 前端权限体系重构（前端按钮显隐维持现状，只保证与后端一致）
