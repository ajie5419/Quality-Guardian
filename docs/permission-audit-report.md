# 权限系统摸底报告（越权删改问题）

> 2026-08-16，依据代码全量扫描（apps/backend，342 个 API 端点、33 个业务模块）得出。对应行动清单 docs/audit-action-plan.md 第 1 项。

---

## 一、核心结论（一句话）

**这个系统的权限设计是"前台权限"而不是"后台权限"：52 个权限码只控制界面按钮显不显示，后端 189 个写操作里约 140 个只验证"登录了没有"，不验证"有没有资格"。** 任何有账号的人（含普通检验员）都能直接调用接口删除/修改全厂核心质量数据。

## 二、数字摸底

### 1. 全部 342 个 API 端点的保护情况

| 分类 | 数量 | 说明 |
| --- | --- | --- |
| 无需登录（公开） | 16 | 登录/注册、匿名报检、匿名上传、文件访问等 |
| 仅管理员（requireSystemAdmin） | 28 | 系统管理类：用户/角色/菜单/部门/字典/日志等 |
| 权限码校验（service 层） | ~4 个业务点 | 不合格品项、车辆验收删除、工单要求、物料审批 |
| 其余 | **~294** | 任何登录用户均可调用（含全部读接口） |

### 2. 写操作（增删改）的保护情况——问题核心

| 分类 | 数量 | 说明 |
| --- | --- | --- |
| 写端点总数 | 189 | post + put + delete + patch |
| 匿名可写（无需登录） | 5 | 匿名报检提交/借还计量器具（业务上刻意公开） |
| 仅管理员 | 23 | 系统管理类 |
| **仅登录、零业务校验** | **~157** | **其中约 140 个连 service 层也没有任何权限/所有权校验** |

### 3. 按业务模块看"零校验"的严重程度

**18 个模块的 service 层完全没有任何权限校验关键词**，包括核心质量模块：

- 🔴 **检验记录**（inspection/records）：删除/修改检验记录——检验记录 = 质量档案，可被任意账号软删除
- 🔴 **计量器具**（metrology）：删除/修改台账、检定计划、借还记录
- 🔴 **质量策划**（planning）：BOM、DFMEA、ITP、检验表单 全部增删改
- 🔴 **监督检查**（supervision）：项目、问题、报告 全部增删改
- 🔴 **焊工资质**（welder）、**知识库**（knowledge）、**工单**（work-order，写入部分）
- 🟠 售后（after-sales 写）、供应商评分（supplier 写）、质量损失（部分有）、工作台等

### 4. 权限码体系盘点

- 权限码（authCode）共 **52 个**，声明在模块菜单/按钮定义里
- **后端实际消费权限码的业务点只有 4 个**：不合格品项（6 码，读写全覆盖，唯一完整范式）、车辆调试验收删除、工单质量要求、检验物料审批
- 其余 48 个权限码**只被前端菜单/按钮消费**（决定按钮显隐）——这就是"前台权限"的本质

### 5. 数据范围（按部门隔离）现状

- 6 个模块声明了数据范围（after-sales、inspection、quality-loss、supplier、work-order…）
- **默认关闭**（环境变量 DATA_SCOPE_V2 默认 false，未开启时全员可见全库）
- 即使开启，消费点几乎都在**读路径**；写路径只有 quality-loss 一个模块做了范围校验
- **inspection（最大的模块）声明了数据范围但 service 层零消费**——检验记录/不合格品永远全员可见

## 三、为什么变成这样（根因）

1. **RBAC 定位偏差**：权限体系从一开始就是"菜单权限"（生成菜单、控制按钮显隐），从未设计"后端强制校验"；52 个码配了表、配了回填脚本，唯独没接 API 层
2. **无新增即登记的门禁**：新增端点没有任何"必须声明权限"的检查——架构门禁查行数、查导入、查错误码，就是不查权限；于是每个新端点都默认"登录即可"，问题随功能持续复制
3. **校验实现五套并存**：requireSystemAdmin / 权限码 / 自建 access 服务 / dataScope / createdBy 手动校验——没有统一框架，新模块不知道该用哪套，多数选择不用
4. **数据范围半成品**：默认关闭 + 只覆盖读 + 大模块未接入，实际处于"写了规范没生效"状态
5. **历史演进**：业务先跑起来、权限后补，补丁式地给个别模块（issues、vehicle-commissioning）加了校验，形成"少数有、多数无"的现状

## 四、修复方向（抓手）

1. **统一授权框架**：写端点"声明制"——模块声明文件里声明每个写端点需要的权限码/所有权规则，框架中间件统一强制；声明缺失 = 默认拒绝
2. **门禁拦截**：新增写端点未声明权限 → CI 拦截（增量控制，存量另行清债）
3. **存量分批补齐**：以"不合格品项"模块为范式模板（权限码 + 创建人所有权 + 数据范围三层），按模块分批迁移：先检验记录/计量/策划/监造/焊工/知识库/工单，再其余
4. **数据范围启用**：DATA_SCOPE_V2 开启 + inspection 接入 + 写路径统一走框架
5. **优先级参考**：删除 > 修改 > 新增；质量档案类（检验记录/不合格品/质量损失）> 业务台账 > 配置类

## 五、风险提示

- 以上结论基于**代码静态扫描 + 人工抽读**；"生产环境是否已被利用"需查 `audit_logs` 操作日志确认（行动清单第 1 项后半步）
- 修复前，**离职/禁用账号 7 天内仍可用旧 token 调用这些接口**（token 无服务端吊销），建议同步处理
